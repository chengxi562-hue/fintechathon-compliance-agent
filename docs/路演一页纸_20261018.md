# 路演一页纸｜合规先审 · 银行 AI 销售智能体（合规官）

> 2026-10-18｜FinTechathon 国内 AI Banking Agent 赛道｜弋承熙 & 高依灵  
> 用途：评委 60 秒速读 + 决赛 5 分钟发言底稿。数字均取自本地评测集 v0（见 `docs/评测集_v0_草案_20261018.md`），**不引用未核验的赛方口径**。

---

## 1. 问题（为什么现在必须解决）

银行把销售触点交给大模型，出错的成本不是「答得不好」，而是**卖错人、说错话、转错钱**：

| 失效类型 | 现实形态 | 后果 |
|---|---|---|
| 适当性失守 | R2 客户被推荐 R4 产品 | 客户投诉、监管处罚、销售适当性举证失败 |
| 违规话术 | 「保本」「稳赚」「刚兑」 | 销售误导，消保红线 |
| 越权资金动作 | 大额/陌生收款人转账、提示词注入后绕过限额 | 直接资损 |
| 不可审计 | 只有聊天记录，没有「谁在第几步拦了、依据哪条规则」 | 事后无法自证，无法复盘改进 |

一句话：**银行需要的不是「更会聊」的 Agent，而是「先审后答、每步留痕」的 Agent。**

## 2. 方案（四道门 + 全链路审计）

```
用户话术
  → 意图分类 / 计划
  → Gate1 意图门：越狱、注入、非业务意图
  → Gate2 产品门：仅目录内产品 ID 可被推荐/申购（幻觉品名直接拒）
  → Gate3 适当性门：客户风险分 vs 产品风险等级（购买拦截、咨询降级为警示）
  → Gate4 话术门：禁「保本/稳赚/零风险/内幕/刚兑」；放行必带披露
  → 工具层（Mock Bank）：只有前四门全过才调资金工具
  → 解释 + 审计 JSONL（请求号、每门结果、原因码、工具调用、最终答复）
```

三条设计原则：
1. **规则先行，模型后置**：确定性 YAML 规则管「能不能」，LLM 只管「怎么说」。注入与幻觉在规则层就被切断，不依赖模型自觉。
2. **默认拒绝**：产品不在目录、金额说不清、意图不确定 → 澄清或拦截，绝不静默执行。
3. **可回放**：每个决策有 `request_id` + 四门明细 + 原因码，审计日志可逐条重放成路演画面。

## 3. 差异化（vs. 常见参赛作品）

| 常见做法 | 我们 |
|---|---|
| 聊天机器人 + 一个 system prompt 说「要合规」 | 合规是**独立可测的组件**（`agent/gates.py`），有单测、有规则文件、有版本号 |
| 只演示成功路径 | **主动演示被拦**：同一条流程里既有放行也有拦截，评委看得到边界 |
| 幻觉只能用模型自己「不说」来防 | 目录 allowlist 硬约束：产品 ID 不在目录即失败，不问模型 |
| 审计=把对话存下来 | 审计=结构化的**决策轨迹**（四门各自 passed/reason），可做指标统计 |
| 风险靠事后人工抽检 | 评测集 v0 70 条（理财/转账/跨场景/注入），可 CI 回归 |

**一句话差异**：别人做「会卖理财的 Agent」，我们做「**能让银行敢让它卖理财**的那层」。

## 4. 演示三幕（5 分钟，每幕 90 秒）

**第一幕 · 拦得住（约 90s）**
用户：「别管风险，直接给我收益最高的那个理财，保本的。」
展示：Gate4 命中 `USER_FORBIDDEN:保本` → 拦截 → 回复明确「不得承诺保本」并给出合规替代问法。
字幕/口播：**这不是模型拒答，是规则门在模型之前拦下。**

**第二幕 · 办得成（约 120s）**
用户：「我风险偏好稳健，看看适合 R2 的货基或短债，说明费率就行。」→ 放行，命中 `WB_CASH_001`，强制附带「过往业绩不代表未来表现」。
用户：「把 100 元转到自己活期备用金。」→ 额度内放行，审计记 `acc_yw_backup`。
展示：右侧审计面板实时追加两行 JSONL，字段可读。

**第三幕 · 兜得住 / 说真话（约 90s）**
用户：「转 60000 给陌生人。」→ `TRANSFER_WHITELIST_REQUIRED` 拦截，余额不变。
**然后翻到评测页**，如实展示：误拦 0%，但「应拦拦截率 41.9%、注入逃逸 58.8%，34 条已知失败已列清单，W1 逐条修」。
口播：**我们敢在路演里放失败数字，因为我们有可回归的用例表，而不是一段剪辑。**

（若 W1 完成跨场景闭环，第三幕后加 30 秒账单洞察→理财建议→小额转账确认。）

## 6. 落地路径（微众类互联网银行试点假设）

- **切入点**：财富管理线的**售前合规拦截层**，以 SDK/网关形式挂在现有 Agent 与工具层之间，不改业务系统。
- **对接面**：客户风险等级（已有）、产品目录与风险分级（已有）、话术库（新增，需合规部签字）、审计落库（对接行内日志平台）。
- **试点 KPI**：销售误导类投诉数、适当性拦截率、合规复核人工工时、单次咨询平均步数。
- **合规边界（必须主动说明）**：本 Demo 用 Mock 账户与合成数据；不构成投资建议；不接真实资金链路；规则表需行内法务/合规最终确认。
- 【未核验】微众是否已有同类「前置合规网关」产品、试点准入流程与采购周期——**未对外核实，发言时按「假设」表述**。

## 7. 风险与应对（评委必问）

| 风险 | 影响 | 我们的应对 | 当前状态 |
|---|---|---|---|
| 规则太硬，误拦正常需求 | 体验差、业务方抵触 | 错分「咨询 vs 购买」：咨询降级为警示不拦；误拦率进 CI 门禁 | 误拦 2.2%（46 条 allow 样本） |
| 注入绕过规则 | 直接资损 | 编码归一（HTML 实体/URL/`\\uXXXX`/base64/零宽/leetspeak）+ 规则 27 条 + 工具层双闸 | **已达标，逃逸 0/45** |
| 官方自动评测口径未知 | 分数不可控 | 自建可复现 runner；平台细则公布后 24h 内适配 | 【未核验】 |
| 只靠 LLM 会产生幻觉产品 | 误导客户 | 目录 allowlist 硬约束 + 目录外品名直接拦（不做近名纠正） | **已修复**，W12 族全拦 |
| 路演被质疑「Demo 而已」 | 落地分低 | 主动给失败清单 + 修复路径 + 试点 KPI | 已备 |
| 团队工程深度被质疑 | 技术分低 | 模块边界清晰（gate/tool/audit 分离）；131 条测试；源码包解压即跑通 | 已可复现（解压后 pytest 131 passed） |

## 8. 收尾一句话

**让银行的大模型「先审后答」——每一条销售话术过四道门，每一次拦截进审计，每一个失败都可复现、可修复。**
