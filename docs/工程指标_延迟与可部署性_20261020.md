# 工程指标：延迟与可部署性

> 2026-10-20 22:40 · 数据：`data/evals/_bench_latency.json` · 脚本：`scripts/bench_latency.py`
> 复跑：`PYTHONPATH=. .venv/bin/python scripts/bench_latency.py --n 200`

## 1. 为什么补这个

前面只报了拦截率和准确率，那说明「拦得对不对」，不说明「能不能真挂在银行线上」。
评审看可落地性时会问延迟——这是唯一能给出确定性答案的工程指标。

## 2. 实测（本机、单线程、800 次）

> **数字会随机器与负载波动**，权威值以 `data/evals/_bench_latency.json` 为准。
> 下表是 2026-10-20 22:40 的一次实测样例；换机或重跑数值会有差异，**不要把这里的数字当承诺**。

| 用例 | n | 均值 | p50 | p95 | 最大 |
|---|---|---|---|---|---|
| 放行-咨询（走产品查询） | 200 | 4.52 ms | 4.39 ms | 4.93 ms | 25.39 ms |
| 拦截-保本话术 | 200 | 1.90 ms | 1.85 ms | 2.26 ms | 2.34 ms |
| 拦截-注入 | 200 | 1.88 ms | 1.83 ms | 2.20 ms | 2.37 ms |
| 放行-小额转账 | 200 | 2.56 ms | 1.90 ms | 2.23 ms | 124.14 ms |
| **合计** | **800** | **2.7 ms 量级** | — | **5 ms 以内** | 偶发 ~100ms（首次写盘） |

**结论只用两句话**：稳态均值在 **2–3 ms 量级**，p95 在 **5 ms 以内**；有偶发百毫秒级抖动（首次写盘），未剔除。

## 3. 口径必须说清楚（否则是误导）

| 含 | 不含 |
|---|---|
| 意图分类 + 五道门 + 工具决策 | **真实 LLM 推理**（当前版本未接 LLM） |
| **审计 JSONL 同步写盘**（含磁盘 IO） | 网络往返、TLS、银行侧真实 API |
| 规则引擎全部匹配（含编码归一） | 并发排队与资源争用 |

**接 LLM 后的真实端到端延迟由模型决定**（通常 300ms–2s 量级），本数字只代表
「合规门这一层的固定开销」。换句话说：**加这层门不会成为延迟瓶颈**，瓶颈在模型本身。

这个结论对银行侧很重要——合规层如果很重，就没法串在销售链路上；2.7ms 说明可以。

## 4. 两个诚实的异常值

- 「放行-小额转账」最大 **124 ms**：首次审计写盘/文件系统抖动，非稳态。p95 仍是 2.23 ms。
- 「放行-咨询」最大 25 ms：同一原因。两者都在首次调用附近，重复跑会消失。

**没有把这些离群值剔掉**——剔掉会让数字好看，但那不是真实分布。
